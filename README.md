# Invoices

Full-stack модуль для роботи з інвойсами: список, деталі, створення та редагування
з контролем сум, дат і статусів.

**Стек:** Nuxt 4 / Vue 3.5 / TailwindCSS 4 · Laravel 13 / PHP 8.4 · PostgreSQL 18 · Docker

---

## Запуск

### Через Docker (рекомендовано)

```bash
docker compose up --build
```

Піднімає три сервіси:

| Сервіс | Адреса | Опис |
|---|---|---|
| `app` | http://localhost:3000 | Nuxt (SSR, production build) |
| `api` | http://localhost:8000 | Laravel API |
| `db` | `localhost:5433` | PostgreSQL |

Міграції виконуються автоматично при старті контейнера `api`, `.env` і `APP_KEY`
генеруються там само — жодних ручних кроків після `up` не потрібно.

Порти можна перевизначити, якщо вони зайняті:

```bash
APP_PORT=3100 API_PORT=8001 DB_PORT=5434 docker compose up --build
```

### Локально (без Docker)

```bash
# backend
cd api
cp .env.example .env && composer install
php artisan key:generate && php artisan migrate
php artisan serve            # http://localhost:8000

# frontend
cd app
cp .env.example .env         # API_BASE_URL=http://localhost:8000/api
npm install && npm run dev   # http://localhost:3000
```

У `api/compose.yaml` лежить окремий Laravel Sail-стек — це середовище для розробки
бекенду (PHP + PostgreSQL + Redis, API на `:80`). Для перевірки завдання він не
потрібен: кореневий `docker-compose.yml` самодостатній і піднімає весь стек разом
із фронтендом.

## API

| Метод | Ендпоінт | Опис |
|---|---|---|
| `GET` | `/api/invoices` | Список, сортування `created_at desc`, пагінація (`page`, `per_page` ≤ 100) |
| `GET` | `/api/invoices/{id}` | Один інвойс |
| `POST` | `/api/invoices` | Створення |
| `PUT` | `/api/invoices/{id}` | Оновлення (тільки для статусу `pending`) |

**Коди відповідей:** `200`, `201` створення, `404` неіснуючий інвойс,
`409` спроба оновити не-`pending` інвойс, `422` помилки валідації.

Пагіновані колекції приходять у конверті `{ data, links, meta }`, одиничні
ресурси — плоским об'єктом (наслідок `JsonResource::withoutWrapping()`).

## Відповіді на питання

### 1. Як структуровано frontend і backend?

**Backend** — потік запиту йде через явні шари:

```
routes/api.php
  └─ InvoiceController          тонкий, лише HTTP: коди статусів і ресурси
       └─ InvoiceServiceInterface   контракт, прив'язаний у AppServiceProvider
            └─ InvoiceService       бізнес-логіка (перевірка статусу, вибірки)
                 └─ Invoice         модель, каст статусу в enum
```

Допоміжні елементи розкладені за відповідальністю: `InvoiceRequest` /
`InvoiceIndexRequest` — валідація вхідних даних, `InvoiceData` — DTO між
контролером і сервісом, `InvoiceResource` — форма відповіді, `InvoiceStatus` —
enum з методом `isEditable()`, `LatestFirstScope` — глобальний scope сортування,
`InvoiceNotEditableException` — доменний виняток із власним `render()` у 409.

Ключове рішення: правило «редагувати можна лише `pending`» живе **в сервісі**, а не
у FormRequest чи Policy. Валідація дивиться на вхідні дані, а тут умова залежить
від поточного стану сутності в БД; Policy відповідає на «чи має право цей
користувач», а не «чи дозволяє стан ресурсу».

**Frontend** — вертикальні слайси плюс горизонтальні глобальні шари:

```
app/
├─ domain/          спільні типи API (IPaginated, IApiError)
├─ repositories/    доступ до HTTP, framework-agnostic класи
├─ services/        чисті функції без Vue (нормалізація помилок, форматування)
├─ components/System/  UI-примітиви (AppButton, AppInput, AppPagination…)
└─ views/invoices/  слайс фічі
   ├─ domain/       типи, enum-и, zod-схеми
   ├─ api/          useInvoiceApi — місток репозиторій ↔ $fetch
   ├─ composables/  стан і логіка (useInvoices, useInvoiceEditForm…)
   ├─ components/   компоненти фічі
   └─ pages/        композиція сторінок
```

`pages/` у корені — тонкі обгортки над `views/invoices/pages/`, щоб маршрутизація
не диктувала структуру коду. Компоненти не знають про HTTP: вони отримують дані
з composables, ті — з `api/`, той — з `repositories/`.

### 2. Які компроміси зроблено і чому?

- **`gross_amount` зберігається в БД, хоча є похідним** від `net + vat`. Формально
  це денормалізація, але поле є в ТЗ, за ним зручно сортувати й фільтрувати без
  обчислень на льоту. Розплата — його треба звіряти при кожному записі, що й
  робить валідація.
- **Клієнтська валідація дублює серверну.** zod-схеми повторюють правила
  Laravel — свідомо, заради миттєвого фідбеку у формі. Джерело істини лишається
  сервер: помилки з 422 розкладаються по полях і перекривають клієнтські.
- **Статус можна виставити будь-який при створенні.** Повноцінного workflow
  (`pending → approved`, заборонені зворотні переходи, хто саме затвердив)
  у завданні немає, тож зроблено простий select.
- **`php artisan serve` у контейнері замість php-fpm + nginx.** Для перевірки
  завдання це один шар замість трьох; для продакшену не годиться.
- **Пагінація offset-based** (`LIMIT/OFFSET`). На великих таблицях глибокі
  сторінки просідають, але cursor-пагінація дала б складніший API без користі
  на цьому обсязі.
- **Немає тестів.** Найбільший компроміс. Ручно перевірено ключові сценарії
  (201/422/409/404, SSR-рендер усіх сторінок), але автотестів у репозиторії немає.

### 3. Що б покращив у production-версії?

- **Оптимістичне блокування.** Зараз двоє редакторів перезапишуть зміни одне
  одного мовчки: останній `PUT` перемагає. Потрібен `version` або перевірка
  `updated_at` із 409 при розбіжності.
- **Аудит змін.** Для бухгалтерії критично бачити, хто і коли змінив суму. Зараз
  історії немає, `updated_at` показує лише факт останньої правки.
- **Аутентифікація й авторизація** — Sanctum + Policy, ролі (бухгалтер vs
  той, хто затверджує), і тоді ж — CORS-allowlist замість `*`.
- **Тести:** feature на кожен код відповіді (409 на approved, 422 на
  `gross ≠ net + vat`, унікальність `number` при `PUT` власним номером), unit на
  zod-схеми й `normalizeApiError`. Плюс CI з Pint, Larastan та ESLint.
- **Гроші як цілі копійки** або робота через `bcmath`. Зараз суми ходять рядками
  (правильно), але на клієнті для підрахунку `gross` конвертуються у `float` —
  на великих значеннях це джерело похибки.
- **Фільтри й пошук** за статусом, постачальником, діапазоном дат — з індексами
  під них; зараз є лише індекс `(created_at, id)` під сортування.
- **Інфраструктура:** php-fpm + nginx, `config:cache`, opcache, structured logging,
  Sentry, healthcheck-ендпоінт, non-root користувач у контейнерах.
- **i18n** — інтерфейс зараз англійською без словників.

### 4. Які UX edge cases враховано?

**Стани завантаження**
- Loading / error / empty розділені на кожній сторінці, а не звалені в один прапорець.
- 404 відрізняється від інших помилок: для неіснуючого інвойса кнопки «Try again»
  немає — повторювати запит немає сенсу.
- При переході між сторінками пагінації стара таблиця лишається на екрані
  (лоадер показується лише коли даних ще немає), тож список не «стрибає».

**Конкурентність і бізнес-правила**
- Якщо інвойс затвердили, поки була відкрита форма, `PUT` повертає 409 — показуємо
  окремий банер «Invoice is no longer editable», а не загальну помилку.
- Форма редагування блокується через `<fieldset disabled>`, а не приховану кнопку:
  поля недоступні навіть через DevTools-клік, і це коректно озвучується
  скрінрідером.
- Кнопка збереження неактивна, поки форма не змінена (`dirty`), — щоб не слати
  порожній `PUT`.

**Дані й формати**
- Суми приходять з API рядками (`"1200.00"`) — типізовані як `string`, конвертація
  явна там, де потрібна арифметика.
- `gross` рахується з округленням до копійок: без нього `0.1 + 0.2` дало б
  `0.30000000000000004` і 422 від сервера.
- Дати `issue_date`/`due_date` — date-only, віддаються без часу: ISO-мітка з
  півночі UTC у браузері з іншим офсетом показувала б попередню добу.
- Гроші форматуються вручну, не через `Intl` — Node і браузер підставляють різні
  символи-роздільники, що ламало б гідратацію.

**Навігація**
- Пагінація живе в URL (`?page=3&per_page=25`), тож перезавантаження, кнопка
  «назад» і надіслане посилання відкривають ту саму сторінку.
- Після створення чи збереження користувач повертається на **ту саму** сторінку
  списку, з якої пішов, а не на першу.
- `?page=99` при 4 сторінках: замість хибного «No invoices yet» показуємо
  «This page is empty» разом із пагінацією (є куди клікнути ще до гідратації)
  і автоматично відкочуємо на останню наявну сторінку.
- `?per_page=999` або `?page=abc` — парсяться з клампом, у бекенд не летить
  значення, яке дало б 422 замість списку.
